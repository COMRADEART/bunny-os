## Why not ORAS

The brief suggests an established OCI artifact tool "where appropriate", and
names ORAS. The snapshot is published as a single-layer OCI image built `FROM
scratch` with podman and pushed with skopeo instead.

ORAS would have to be added to the builder image. That changes the builder
digest, which is the pin every qualification build asserts and which both hosted
builders must present — a rebuild, a re-lock and a re-publication, to gain an
artifact media type nothing in this project reads. skopeo and podman are already
pinned, already classified output-affecting, and produce an artifact that is
content-addressed, pullable by digest and verifiable with the same tooling as the
other two inputs.

If a consumer ever needs the artifact media type, that is a reviewed
builder-image change rather than a side effect of a push.

## Retention, and what is not yet known about it

`write-publication-lock.py` records the registry repository, the manifest digest,
the full blob inventory with sizes, the publishing account and the recovery
process. Three fields are written as `unverified` rather than asserted:

```text
deletionProtection    unverified
accessPolicy          unverified
backupLocation        the local retention store — a copy, on one machine
```

GitHub package retention, deletion and visibility are repository settings, not
properties of a push. An untagged-version cleanup policy can delete a digest
silently, and every build pinned to it would then fail. Writing "protected"
without reading the settings back would be the kind of claim this project exists
to avoid; `unverified` is the honest value until something checks.

The backup is the local retention store. It is a copy, not a second independent
location, and it does not by itself satisfy independent availability.

## Verification plan once published

1. record the pushed manifest digest and compare it to the retained one
2. clear local registry and container caches
3. pull by digest
4. recompute every blob's digest from the pulled bytes
5. verify the snapshot manifest signature
6. re-derive every package checksum from the RPMs themselves
7. re-verify every Fedora RPM signature with `rpmkeys --checksig`
8. reconstruct the repository from the pulled content
9. perform an offline install with `--network=none` and `gpgcheck=1`
10. account for all 474 locked packages

Steps 3 to 10 run again on a clean hosted runner, which is
`COLD_PULL_INPUT_VERIFICATION_REPORT.md`. Steps run here would prove the push
worked; run there they prove the inputs are retrievable, which is the claim that
matters.
