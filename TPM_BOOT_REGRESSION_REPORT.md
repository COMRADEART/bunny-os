# TPM boot regression report

Occurrence counts for every cell of the `tpmq-1` matrix against the frozen
qualified artifact (QCOW2 `0b7dd90d…`, archive `29e54aaf…`, Commit G).
Machine-readable: `qualification/tpm/evidence/matrix-summary.json`; the
per-cell table below is regenerated by
`qualification/tpm/scripts/summarise_matrix.py`.

Reading rules for this report:

* Counts, never a bare PASS. Each cell states boots attempted and how far
  each boot got.
* `D` marks a diagnostic cell: TCG, a non-pinned CPU model or machine
  version, or a separately sourced disk. A diagnostic pass qualifies
  nothing on the supported path.
* `resets` counts **guest-initiated** resets only. A platform reset issued
  through QMP is not a guest reset and is counted as zero here; the
  qemu-reset cells prove the second boot instead.
* Failed units are counted separately from boot success, below. An
  intermittent `gdm` or `avahi` failure is a different fact from a TPM
  reset, and merging them would hide both.

### Reading the rows that look odd

Several rows are investigation controls rather than matrix cells, and some
carry superseded runs. Nothing here was re-scored after the fact — a record
re-scored later is a record that means nothing — so where a verdict rule was
wrong, the cell was re-run and both runs are kept.

* **`crb-fresh-stop`, `tis-fresh-stop` (1 boot each, 0/1).** The original
  classification runs. They stopped at the reset on purpose — that was their
  job — and were judged by the boot-completion rule in force before the
  matrix distinguished a reproduction expectation from a boot expectation.
  The `*-repro-stop` cells re-run the same experiment under the corrected
  rule, 3/3 each with a classified reset.
* **`fw-only-crb` (6 boots, 5/6).** The one failure is its first run, which
  predates the stability expectation and was scored INCONCLUSIVE despite
  behaving exactly as a firmware control should. The other five are clean
  (`TPM_FIRMWARE_CONTROL_REPORT.md`).
* **`tcg-no-tpm` (6 boots, 3/6).** Runs 1–3 were downgraded to INCONCLUSIVE
  by a reader-death rule that fired on the harness's own clean shutdown — a
  defect in this pass's own instrumentation, found by reading the results
  instead of trusting them. Their transcripts show exactly what the cell was
  asked to show, so the measurement was never in doubt; only the verdict rule
  was. Runs 4–6, under the corrected rule, are 3/3: booted to
  `graphical.target` under pure emulation with no TPM and **zero resets**.
* **`smm-on-crb` (6 boots, 6/6).** Runs 1–3 were not flagged diagnostic,
  though SMM on deviates from the supported configuration. Runs 4–6 carry
  the flag. All six reset exactly once and reach `graphical.target`; a
  varied run presented as the pinned one is what the flag exists to prevent,
  not a different result.
* **`crb-fresh-continue`, `crb-reuse-vars` (1 boot each).** The two
  discriminating experiments that identified the mechanism, kept because the
  root-cause statement cites them.
* **`fedora-*` rows show 0 in the GRUB and graphical columns.** The
  comparator is a Fedora *Cloud* image: its bootloader does not print the
  `GRUB version` banner this harness keys on, and it has no graphical
  target to reach. Its boots are judged on `multi-user.target`, which they
  reach. The column is a marker count, not a claim that GRUB was absent.

### What the diagnostic comparators established

Each varied one thing against the supported configuration and reported
whether the restoration reset still occurred:

| Variation | Reset still occurs? | What it rules out |
| --- | --- | --- |
| TCG instead of KVM (`tcg-crb-fresh`, 3/3, 1 reset each) | yes | hardware acceleration, and any KVM-specific timing |
| Named generic CPU instead of `-cpu host` (`cpu-named-crb`, 3/3) | yes | the CPU model |
| `pc-q35-10.1` and `pc-q35-9.2` (3/3 each) | yes | the machine version |
| SMM enabled (`smm-on-crb`, 6/6, 1 reset each) | yes | SMM configuration |
| A stock Fedora Cloud 44 disk (`fedora-crb-fresh-repro`, 3/3) | yes | anything specific to the Bunny artifact |
| No TPM, under TCG (`tcg-no-tpm`, runs 4–6, 3/3, 0 resets) | no | — the reset needs a TPM even without KVM |
| No disk at all (`fw-only-*`) | no | — the firmware alone never resets |

Every variation that leaves a TPM present and the variable store fresh
reproduces the reset; every variation that removes one of those two removes
it. That is the shape the `fallback.c` mechanism predicts, measured across
seven independent axes.

## The supported regression cells

These are the cells the qualification gate requires, at five boots each,
with the no-TPM control paired against every one of them:

```text
no-tpm-cold        TPM absent,   fresh vars,      cold boot
crb-fresh-cold     tpm-crb,      fresh vars,      fresh TPM state, cold boot
tis-fresh-cold     tpm-tis,      fresh vars,      fresh TPM state, cold boot
crb-reused-cold    tpm-crb,      restored vars,   reused TPM state, cold boot
tis-reused-cold    tpm-tis,      restored vars,   reused TPM state, cold boot
crb-qemu-reset     tpm-crb,      restored vars,   platform reset after target
tis-qemu-reset     tpm-tis,      restored vars,   platform reset after target
```

The fresh-variable cells are expected to reset exactly once: that is shim
fallback's designed boot-option restoration reboot, which the boot then
survives (`TPM_GRUB_RESET_ROOT_CAUSE.md`). The reused-variable cells are
expected to reset zero times. A cell that missed its expectation in either
direction fails; the expectation is declared in the matrix definition, not
inferred after the fact.

## An asymmetry in the state matrix, stated rather than glossed

The four fresh/reused combinations of OVMF variables × TPM state were run
in full for `tpm-crb` (`crb-fresh-cold`, `crb-reused-cold`,
`crb-fresh-vars-reused-state`, `crb-reused-vars-fresh-state`). For
`tpm-tis` only the two diagonal combinations were run
(`tis-fresh-cold`, `tis-reused-cold`).

The justification, which is an argument and not a measurement: every paired
CRB/TIS cell that was run produced identical behaviour, and the mechanism —
`fallback_should_prefer_reset()` testing for the presence of a TCG protocol
— cannot distinguish the two interfaces, because both expose the same
protocol to the same firmware. The two missing TIS cells would test a
variable the code path does not read.

That is a reasoned expectation, not evidence. If a future pass needs TIS
state-combination evidence, it must run the cells rather than cite this
paragraph.

## What is not covered, and is therefore not claimed

**OS-level `reboot` from a logged-in session is not measured.** Driving it
needs harness login injection, which does not exist: `ctrl-alt-del` sent
through QMP does not reach PID 1 while the graphical session holds the VT
(measured — the same sequence rebooted one boot and was swallowed by the
next, across six retries), and Fedora masks sysrq reboot by default. Rather
than keep a cell that would silently never fire, the guest-reboot cells were
withdrawn and their partial runs deleted. Reboot behaviour is covered from
two other directions that are real:

* **Guest-initiated reset with a TPM attached** — the fresh-variable cells.
  Shim's `ResetSystem(EfiResetCold)` is an in-guest reset request, observed
  through QMP as `guest-reset`, after which the same VM boots to
  `graphical.target` on the same TPM and firmware state.
* **Platform reset** — the qemu-reset cells: a QMP `system_reset` after the
  first boot reaches its target, requiring a complete second boot.

This limitation is carried in the gate's own output
(`import_tpm_results.py`, `COVERAGE_LIMITATIONS`), not only in this report,
so a reader of the machine-readable verdict cannot mistake it for full
coverage.

## Failed units, quantified separately

<!-- BEGIN FAILED UNITS -->
The serial console reported no failed units on any of 93 boots. This is the console's view, not the journal's: a unit that failed quietly would not appear here.
<!-- END FAILED UNITS -->

**What this measurement is, and what it is not.** The counts above are
parsed from the serial transcript of each boot: systemd's `[FAILED] Failed
to start …` and `unit: Failed with result …` console output. They are not
the journal. The authoritative per-unit classification across boots is
`dispose_failed_units.py`, which reads `systemctl --failed` and the journal
from the booted disk offline, and it was not re-run in this pass — this pass
is about the TPM boot path, and re-deriving the unit landscape would have
meant mounting a per-run overlay for every boot in the matrix.

So the honest statement is narrow: across these boots, the serial console
reported the failures counted above, and no TPM cell reported more of them
than the no-TPM control. The BrlAPI pass's finding stands unchanged —
`gdm` and `avahi-daemon` fail intermittently on identical images — and
nothing here contradicts or re-qualifies it. What this report does claim is
that no unit failure it observed correlates with TPM presence, interface or
state.

## Reset classifications

<!-- BEGIN CLASSIFICATIONS -->
* `BOOTLOADER_REBOOT_COMMAND` — 46 runs
* `HOST_TERMINATED` — 1 runs
<!-- END CLASSIFICATIONS -->

Every reset in this matrix is classified. `UNKNOWN` blocks the gate, and no
run ended there.

`BOOTLOADER_REBOOT_COMMAND` is the restoration reboot, in every cell that
boots a disk through the fallback path with a TPM attached. The single
`HOST_TERMINATED` is `fw-only-crb-001`, the first firmware-only control:
it ran before the stability expectation existed, so the harness's own
end-of-window quit was classified as if it were an event. The five later
firmware-only runs carry no classification because nothing terminal
happened in them, which is what a firmware control passing looks like.
