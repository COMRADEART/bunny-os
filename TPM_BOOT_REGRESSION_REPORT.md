# TPM boot regression report

Occurrence counts for every cell of the `tpmq-1` matrix against the frozen
qualified artifact (QCOW2 `0b7dd90d…`, archive `29e54aaf…`, Commit G).
Machine-readable: `qualification/tpm/evidence/matrix-summary.json`; the
per-cell table below is regenerated by
`qualification/tpm/scripts/summarise_matrix.py`.

Reading rules for this report:

* Counts, never a bare PASS. Each cell states boots attempted and how far
  each boot got.
* `D` marks a diagnostic cell: TCG, a non-pinned CPU model or machine
  version, or a separately sourced disk. A diagnostic pass qualifies
  nothing on the supported path.
* `resets` counts **guest-initiated** resets only. A platform reset issued
  through QMP is not a guest reset and is counted as zero here; the
  qemu-reset cells prove the second boot instead.
* Failed units are counted separately from boot success, below. An
  intermittent `gdm` or `avahi` failure is a different fact from a TPM
  reset, and merging them would hide both.

## The supported regression cells

These are the cells the qualification gate requires, at five boots each,
with the no-TPM control paired against every one of them:

```text
no-tpm-cold        TPM absent,   fresh vars,      cold boot
crb-fresh-cold     tpm-crb,      fresh vars,      fresh TPM state, cold boot
tis-fresh-cold     tpm-tis,      fresh vars,      fresh TPM state, cold boot
crb-reused-cold    tpm-crb,      restored vars,   reused TPM state, cold boot
tis-reused-cold    tpm-tis,      restored vars,   reused TPM state, cold boot
crb-qemu-reset     tpm-crb,      restored vars,   platform reset after target
tis-qemu-reset     tpm-tis,      restored vars,   platform reset after target
```

The fresh-variable cells are expected to reset exactly once: that is shim
fallback's designed boot-option restoration reboot, which the boot then
survives (`TPM_GRUB_RESET_ROOT_CAUSE.md`). The reused-variable cells are
expected to reset zero times. A cell that missed its expectation in either
direction fails; the expectation is declared in the matrix definition, not
inferred after the fact.

## What is not covered, and is therefore not claimed

**OS-level `reboot` from a logged-in session is not measured.** Driving it
needs harness login injection, which does not exist: `ctrl-alt-del` sent
through QMP does not reach PID 1 while the graphical session holds the VT
(measured — the same sequence rebooted one boot and was swallowed by the
next, across six retries), and Fedora masks sysrq reboot by default. Rather
than keep a cell that would silently never fire, the guest-reboot cells were
withdrawn and their partial runs deleted. Reboot behaviour is covered from
two other directions that are real:

* **Guest-initiated reset with a TPM attached** — the fresh-variable cells.
  Shim's `ResetSystem(EfiResetCold)` is an in-guest reset request, observed
  through QMP as `guest-reset`, after which the same VM boots to
  `graphical.target` on the same TPM and firmware state.
* **Platform reset** — the qemu-reset cells: a QMP `system_reset` after the
  first boot reaches its target, requiring a complete second boot.

This limitation is carried in the gate's own output
(`import_tpm_results.py`, `COVERAGE_LIMITATIONS`), not only in this report,
so a reader of the machine-readable verdict cannot mistake it for full
coverage.

**What this measurement is, and what it is not.** The counts above are
parsed from the serial transcript of each boot: systemd's `[FAILED] Failed
to start …` and `unit: Failed with result …` console output. They are not
the journal. The authoritative per-unit classification across boots is
`dispose_failed_units.py`, which reads `systemctl --failed` and the journal
from the booted disk offline, and it was not re-run in this pass — this pass
is about the TPM boot path, and re-deriving the unit landscape would have
meant mounting seventy per-run overlays.

So the honest statement is narrow: across these boots, the serial console
reported the failures counted above, and no TPM cell reported more of them
than the no-TPM control. The BrlAPI pass's finding stands unchanged —
`gdm` and `avahi-daemon` fail intermittently on identical images — and
nothing here contradicts or re-qualifies it. What this report does claim is
that no unit failure it observed correlates with TPM presence, interface or
state.
