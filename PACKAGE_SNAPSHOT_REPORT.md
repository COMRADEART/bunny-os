## Why a snapshot exists

Two builders cannot be expected to produce identical images while each resolves
its own package set from a moving repository. Fedora's repositories change daily;
a build that resolved against them would install whatever was current, and a
comparison between two such builds measures the mirror rather than the build.

The snapshot is resolved once, from the retained base, and every subsequent build
installs from it over `file://` with no network access at all.

## Defects found by building it

Each was invisible by reading and is recorded because the class recurs.

| Where | What happened |
| --- | --- |
| `resolve-package-lock.py` | dnf5 rejects `--downloadonly` before the subcommand and rejects `--destdir` on `install` entirely; dnf4 accepted both. The transaction is taken from the libdnf5 cache instead. |
| `resolve-package-lock.py` | the repository id was joined to the filename with `%%`; `rpm -qp` read that as a format escape, collapsed it to `%`, and could not open the file it had just been given. |
| `resolve-package-lock.py` | **Fedora signs `RSAHEADER`, not `SIGPGP`.** Querying `SIGPGP` reported all 474 packages as `unsigned`. A supply-chain lock recording every Fedora package as unsigned is both false and wrong in the dangerous direction. |
| `install-packages.py` | the snapshot repository had `gpgcheck=1` and no key configured, so dnf refused the whole transaction: *"The repository does not have any OpenPGP keys configured."* **This was the check working.** The fix points it at Fedora's own keys; `gpgcheck=0` and re-signing with the development key were both available and both wrong. |

## Signing keys shipped with the packages

The keys are in the snapshot deliberately. A snapshot that could only be verified
by fetching Fedora's keys from the network would reintroduce, at verification
time, the dependency the snapshot exists to remove. `verify-published-inputs.py`
refuses a snapshot that ships no key rather than falling back to a key from
somewhere else.

## Known differences from a remote snapshot

### `repo_gpgcheck=0`

`repo_gpgcheck` verifies a detached GPG signature over `repomd.xml` that a Fedora
mirror provides and a locally generated repository does not.

What replaces it: the snapshot manifest is signed, carries the SHA-256 of
`repomd.xml`, and is verified before the build container starts. `gpgcheck=1`
stays on and every RPM's own Fedora signature is checked at install time.

This is a real difference and is recorded rather than described as equivalent.

### The manifest signing key is a development key

`dev-snapshot-signing1`, Ed25519, held outside the repository.
`release.signing.require_production_key` refuses the `dev-` prefix, so nothing
signed with it can satisfy a release gate. It establishes that the snapshot has
not changed since it was made, and nothing about release authorisation.

### One architecture

Only `x86_64`. An `aarch64` build would fail at verification rather than silently
resolve from upstream, which is correct, and also means this project can
currently qualify one architecture.

## The transaction that installs from it

474 packages install, then one is removed by profile minimisation
(`removePackages: ["toolbox"]`). Both transactions now run under the frozen build
clock; the removal previously did not, and that was one of the two causes of the
database difference (`RPM_DATABASE_DETERMINISM_REPORT.md`).

The removal is verified rather than trusted: anything in `protected.txt` that was
installed before must still be installed after, so a dependency cascade that
silently took recovery, accessibility, firmware, installer or security
functionality with it fails the build instead of shipping.

## What is not established

**Independent availability.** The snapshot exists in one directory on one
machine. Until it is published by digest and pulled from somewhere that does not
already have it, an independent builder cannot use it, and the reproducibility
comparison it enables is between two builds that both read the same disk.

That publication is blocked on a token scope; see
`PACKAGE_INPUT_PUBLICATION_REPORT.md`.
