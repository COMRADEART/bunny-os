# ADR 0017 — x86-64 and ARM64 support

**Status:** Accepted, amended · **Date:** 2026-07-26 · **Spec:** §20.2, §13.9

## Context
C11 requires one Bunny across hardware, and §11 explicitly includes Raspberry Pi-class ARM devices as a real capability profile. The Phase 1 brief asks for an x86-64 and ARM64 strategy.

## Decision
**Split by deployment mode, not by principle.**

- **Safe Linux CLI Preview: Fedora 44 x86-64 only.** This is explicitly pre-V1 and does not redefine D3.
- **Bunny Core (Modes A–C): x86-64 and ARM64 are architecture targets; each release claim is evidence-gated.** ARM matters for Pi-class devices, Apple silicon, and ARM laptops, but a target is not called first-class until a named reference device and continuous runner pass the runtime, sandbox, client, update, and support matrix applicable to that mode.
- **Bunny OS (Mode D): x86-64 first; ARM64 is a gated follow-on.**

The Mode D sequence is a maintainer-capacity decision rather than a claim that ARM64 lacks applications. A one-maintainer project cannot responsibly qualify two kernel, driver, updater, gaming, and application matrices at once. x86-64 also carries the current Steam/Proton and NVIDIA validation burden. The earlier 1.3% Flathub statistic did not have a stable primary dataset and the phrase "app-less OS" overstated what it could prove; both are withdrawn.

## Alternatives
- *ARM64 for Bunny OS at first release* — deferred until the validation gate below; this is a two-way door.
- *x86-64 only everywhere* — rejected: it would exclude Apple silicon and Pi-class devices from Bunny Core, which contradicts C11 and abandons a genuine capability profile the constitution explicitly names.

## Consequences
A Pi-class device may run Bunny as an application (Mode A) with the honest capability profile of §13.9 only after its named tuple passes. Until then it is an experimental remote-client/local-classification target, not a supported agentic execution host.

## Risks
Deferral can become neglect unless the gate is explicit. Re-evaluate when release telemetry shows material ARM demand, a maintained reference device exists, and CI can continuously boot, update, roll back, and run the application-compatibility suite on ARM64.

## Validation required
ARM64 in the existing CI matrix for Bunny Core. Before a Mode D ARM image is announced, the maintained reference device must pass boot/update/rollback, portal, sandbox, and representative application tests for two release cycles.

## Phase 0 principles satisfied
C11 (one Bunny, honest about capability), C15 (inherit the app ecosystem), §11.
