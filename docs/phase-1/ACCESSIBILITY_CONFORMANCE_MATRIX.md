# Bunny OS Accessibility Conformance and Release-Evidence Matrix

**Document status:** Phase 1 release-gate specification  
**Evidence status:** **Unverified - no conformance claim is made by this document**  
**Standard baselines:** WCAG 2.2 Level A and AA; EN 301 549 v3.2.1  
**Applies to:** packaged Bunny Shell, Bunny Box web surface, terminal client, bundled non-web documents, and support services, as scoped below

This matrix turns accessibility requirements into release evidence. A design, automated check, browser-engine capability, or written test case is not proof that the shipped Bunny experience conforms. Every applicable row remains **Unverified - not yet tested** until evidence is captured against an immutable release-candidate build and the exact technology tuple named in the evidence record.

The normative WCAG text and conformance requirements are in the W3C's [Web Content Accessibility Guidelines (WCAG) 2.2](https://www.w3.org/TR/WCAG22/) and [WCAG 2.2 conformance requirements](https://www.w3.org/TR/WCAG22/#conformance-reqs). The European ICT baseline used here is the official ETSI publication of [EN 301 549 v3.2.1](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/03.02.01_60/en_301549v030201p.pdf). EN 301 549 v3.2.1 and WCAG 2.2 are separate gates; satisfying one must not be represented as automatically satisfying the other.

## 1. Evidence rules

### 1.1 Status vocabulary

| Status | Meaning |
|---|---|
| **Unverified - not yet tested** | The row is in release scope, or its applicability has not yet been frozen, but admissible evidence does not yet exist. This is the current status of every non-N/A row in this document. |
| **Fail** | Required evidence was run and at least one applicable assertion failed. A fail blocks release for a mandatory tuple or surface. |
| **Pass for named evidence** | All required evidence passed for the recorded build, exact tuple, locale, settings, and process scope. This is not a product-wide conformance claim. |
| **N/A for this release scope** | A signed scope decision demonstrates that the feature or product class is absent. N/A must name the release and reopen automatically when scope changes. |

No row can move from Unverified directly to a product-level conformance statement. The accessibility DRI must first establish full-page/surface coverage, complete-process coverage, accessibility-supported ways of using technologies, and non-interference across the release support matrix.

### 1.2 Evidence types

| Code | Evidence type | Minimum artifact |
|---|---|---|
| **AUT** | Automated structural or semantic assertion | Test source, machine-readable results, screenshots or accessibility-tree snapshots where relevant, build hash, and failure logs. Automation is regression evidence, not conformance by itself. |
| **MAN** | Manual inspection or interaction test | Script, tester, exact tuple, expected and observed result, media capture where safe, and issue links. |
| **AT** | Assistive-technology test | Exact OS, browser/Shell, accessibility API, AT and version, locale, input settings, script, and observed speech/braille/focus output. |
| **PROC** | End-to-end complete-process test | Start and end state, every page/surface in the process, branch coverage, exact tuple, outcome, and defects. |
| **USR** | Paid disabled-participant evaluation | Recruitment coverage, consent, accommodations, tasks, anonymized findings, severity, disposition, and compensation record. It informs usability and barriers; it does not replace standards evaluation. |
| **DOC** | Documentation/source inspection | Versioned content, format/accessibility check, reviewer, link or artifact digest, and remediation record. |
| **MEDIA** | Time-based media evaluation | Media inventory, captions, transcripts, audio description or alternative, player controls, timing measurements, and manual review. |
| **SEC** | Authentication or consequential-action evaluation | Keyboard/AT flow, cognitive burden, alternatives, error recovery, timeout behavior, and security review. |
| **COMPAT** | Supported-technology compatibility evaluation | Release-candidate build plus an exact tuple from section 2, including platform accessibility settings and any known limitations. |

### 1.3 Evidence owners

| Owner | Accountability |
|---|---|
| **Accessibility DRI** | Owns the matrix, applicability decisions, evaluator independence, defect disposition, and release recommendation. |
| **Bunny Shell** | Owns semantic platform mapping, accessible names/descriptions, focus, input, visual presentation, localization, and Narration Router behavior. |
| **TSM Projector** | Owns deterministic task semantics and preservation of action/state equivalence across list, spatial, animated, static-character, and no-character projections. |
| **Identity and Security UX** | Owns authentication, pairing, consent, permission, approval, revocation, timeout, and consequential-error flows. |
| **Media and Voice** | Owns captions, transcripts, audio description/alternatives, voice controls, and time-based-media inventory. |
| **Localization** | Owns message catalogs, language and direction metadata, locale formatting, and multilingual/bidirectional-text fixtures. |
| **Terminal Client** | Owns the separately scoped linear terminal interaction model, emulator/screen-reader compatibility, prompts, and copy-safe output. |
| **Domain service owners** | Own accessible error/state semantics and complete outcomes for execution, memory, workspace, routing, update, and recovery flows. |
| **Docs and Support** | Owns accessible product documentation, support content, known-limitations disclosure, and accessible contact channels. |
| **Release QA** | Owns build fixation, tuple execution, complete-process regression, artifact retention, and blocking defects. |
| **User Research** | Owns paid disabled-participant recruitment, accommodations, consent, privacy, analysis, and follow-through. |
| **Product Owner and Legal** | Own release-scope assertions and review any regulatory or public conformance wording; they cannot override failed engineering evidence. |

## 4. WCAG 2.2 conformance-requirement matrix

WCAG conformance requires more than passing isolated success-criterion tests. The following five requirements are tracked separately using the W3C's [conformance requirements](https://www.w3.org/TR/WCAG22/#conformance-reqs). All five must be satisfied for the exact release scope before any WCAG 2.2 AA claim is considered.

## 7. Paid disabled-participant coverage

Disabled-participant evaluation is required release evidence, not a testimonial program and not a substitute for expert standards testing. Participants must be paid at a rate set before recruitment, offered the accommodations and remote/in-person format they request, and never required to disclose more medical information than is necessary for access needs. Recruitment records must capture relevant interaction experience without publishing identity or sensitive details.

The sampling plan is approved by User Research and the Accessibility DRI before recruitment. At minimum, each applicable perspective below must have paid participant representation during the major-release cycle, and every high-risk process must be exercised by participants whose access needs it affects. Counts and diversity targets must be recorded in the plan; a single anecdote cannot close a blocker.

| Participant perspective | Minimum coverage focus | Required processes/tuples | Required artifact | Owner | Current status |

## 8. Release evidence package and claim control

For an accessibility gate review, Release QA must produce one immutable evidence index containing:

1. release version, commit, artifact digests, feature flags, migration state, and test date;
2. the exact support tuple versions from section 2, including locale, zoom/scaling, motion/contrast settings, input device and braille display where applicable;
3. every WCAG row's applicability, evidence links, evaluator, observed result and open defects;
4. all five WCAG conformance-requirement decisions, including complete-page/surface and complete-process inventories;
5. an EN 301 549 clause-by-clause applicability ledger and evidence for clauses marked applicable;
6. automated, manual, AT, complete-process, compatibility, media, security, documentation and paid participant artifacts;
7. defect severity, owner, disposition, retest evidence, and disclosed limitation;
8. a non-interference record for every optional/experimental mode and all independent presentation-setting combinations; and
9. an accessible public support statement that names the tested tuples and limitations without claiming untested platforms, browsers, AT, terminal combinations or generated content.

Only the Accessibility DRI and release authority may approve wording for a conformance claim. Until the complete evidence package exists and all applicable blockers are closed, the permitted statement is: **“Accessibility conformance has not yet been verified for this release.”**
