# Bunny OS installation baseline audit

Date: 2026-07-28  
Baseline commit: `8fc27253e448cfe0cbe267231f816012f831ebf0`  
Audit branch: `feature/installer-and-beta-image`

## Executive finding

Phase 1 and Phase 2 provide a Fedora 44 bootc image definition, but this checkout contains no composed OCI, QCOW2, raw disk, ISO, checksum, signature, SBOM, or VM log. The host-only Phase 2 gate passes; the required boot preflight cannot run because there is no image artifact and this Windows host has no Podman, image-builder, systemd, OVMF, or QEMU/KVM. Phase 3 may implement and test non-destructive plans and integration definitions, but no installer, encryption, Secure Boot, beta-image, or hardware support claim is valid until a Linux/KVM evidence run succeeds.

No destructive disk-writing implementation may be enabled from this audit. The selected production executor is the maintained Anaconda/Blivet/bootc path. Bunny-owned code validates typed plans and policy; it does not translate arbitrary frontend strings into root commands.

The build path is OCI Containerfile to unified OSBuild `image-builder`. Release builds require a digest-pinned base, exact tool versions, and a reviewed Fedora snapshot repository. None is provisioned in this checkout.

## Current partition and filesystem layout

The intended disk is GPT/UEFI with an EFI System Partition, `/boot`, and an ext4 bootc root deployment generated by image-builder. `/usr` and `/opt/bunny` are image-managed; `/etc`, `/var`, and `/home` persist. The baseline does not define an install-time separate `/home`, `/var`, or recovery partition. LUKS2 is documented as a production goal but has no installer path or test evidence.

Phase 3's conservative automatic layout is ESP + `/boot` + one LUKS2 container when encryption is selected, with ext4 bootc root and persistent `/var` and `/home` semantics inside the deployment. Exact separate-volume layouts remain unsupported until bootc/image-builder and rollback tests establish them.

## Bootloader and initramfs

The selected boot path is UEFI firmware to Fedora shim and GRUB to a bootc deployment, using Fedora's distribution kernel and dracut initramfs. Legacy BIOS is unsupported. Existing boot entries must be preserved; a shared ESP must never be formatted implicitly. Safe graphics is an unqualified one-shot BLS prototype.

## Image update and rollback

OS updates use signed, monotonic Bunny channel metadata followed by a fixed `bootc switch` to an OCI digest. The prior deployment is retained and `bootc rollback` selects it. Registry signature policy, production keys, boot counting, and update/rollback VM evidence are still missing. User applications and Bunny plugins are separate from OS deployments.

## Recovery design

Recovery consists of a Bunny-independent systemd target in each deployment plus a separately composable headless recovery QCOW2 definition. It offers inventory, rollback selection, diagnostics export, and safe graphics. No independent recovery artifact has been built, signed, or booted. Recovery cannot bypass LUKS, Secure Boot, or administrator authentication.

## Installer framework evaluation

| Candidate | Fedora bootc fit | Storage/encryption | UI/accessibility | Decision |
|---|---|---|---|---|
| Fedora 44 Anaconda Web UI + Blivet + bootc payload | native Fedora path; image-builder can compose a `bootc-generic-iso` | mature UEFI, LUKS, free-space and manual storage paths | current Fedora Web UI, localisation and test ecosystem | selected |
| Calamares | generic live-media installer | capable conventional partitions/LUKS | mature Qt UI | rejected: Bunny would own bootc payload and Fedora policy glue |
| YaST | strong openSUSE stack | mature | mature | rejected: wrong base and policy ecosystem |
| Subiquity/Flutter installer | Ubuntu-focused | mature Ubuntu path | mature | rejected: wrong base and image model |
| systemd-repart/firstboot | good declarative image primitive | useful for deterministic layouts | no complete consumer installer UI | supporting tool only |
| OSBuild/bootc alone | native artifact and deployment tooling | opinionated image layouts | no complete interactive desktop workflow | selected underneath Anaconda |
| custom frontend/backend | maximum branding control | would duplicate dangerous storage code | full accessibility burden | rejected for destructive execution |

Primary sources: [current Anaconda Web UI installation flow](https://anaconda-installer.readthedocs.io/en/latest/anaconda-webui/docs/installation-steps.html), [Fedora 44 Anaconda package](https://packages.fedoraproject.org/pkgs/anaconda/anaconda/fedora-44.html), [Anaconda configuration](https://anaconda-installer.readthedocs.io/en/latest/developer/configuration-files.html), [OSBuild bootc ISO guidance](https://osbuild.org/docs/developer-guide/projects/image-builder/advanced/bootc/isos/), and [unified image-builder bootc usage](https://osbuild.org/docs/developer-guide/projects/image-builder/usage/).

## Encryption readiness

`cryptsetup` is in the package definition and Phase 1 selected LUKS2, password unlock, a user-held recovery key, and optional TPM2 enrolment with an independent fallback. No LUKS volume, Argon2id parameters, keyslot operation, recovery key, TPM PCR policy, or encrypted boot has been tested. Secrets must be passed through protected file descriptors or established installer secret channels, never argv, JSON plans, or logs.

## Secure Boot readiness

Fedora shim, GRUB, kernel, and distribution modules are the intended chain. The derived image has not been built or tested with Secure Boot enabled, and production signing keys do not exist here. Status must therefore be `unknown` or `enabled_with_limitations`; never `supported` until positive and unsigned-negative tests pass. Proprietary NVIDIA modules are not bundled.

## Dual-boot risks

Risks include a wrong target, shared ESP damage, BitLocker recovery, Windows Fast Startup or hibernated NTFS, unsafe shrink, multiple disks, changed firmware boot order, unsupported RAID/LVM, and interrupted writes. Phase 3 enables plan-only detection and free-space planning; filesystem resize and BitLocker resize remain disabled until mature-tool integration and disposable-fixture tests pass. Dual boot is never described as risk-free.

## Firmware and live-session capability

The image definition includes Fedora `linux-firmware`, fwupd, CPU/kernel/Mesa paths, NetworkManager Wi-Fi, BlueZ, PipeWire, and UDisks2. No physical device has been tested. The baseline has no live ISO or installer target; GNOME Shell and recovery profiles are only composition definitions.

## Known installation blockers

- No Phase 1/2 image exists, so normal/recovery/Bunny/Safe Shell/reboot preflight cannot run.
- No Linux builder, KVM/OVMF, loop/mount environment, or image-builder on this host.
- No signed Bunny Linux artifact, release base digest, repository snapshot, update keys, or registry policy.
- Anaconda/bootc ISO package compatibility is unverified for the pinned Fedora 44 compose.
- No LUKS2, TPM2, Secure Boot, UEFI firmware-variable, dual-boot, resize, or destructive fixture execution.
- No accessibility runtime, VM install, upgrade, rollback, or hardware evidence.
- No beta image, checksum/signature, SBOM, or supply-chain scan.

These are release blockers. Host unit tests may qualify schemas and planning behavior only.
